# One Engine, Four Config Points

The same engine serves every use case. No fork. No second codebase. The verticals differ in template and buyer, not machinery.

## The four config points

### 1. Who selects the inputs

- **Consciousness demo:** the builder selected six theories
- **Physics workspace:** the researcher names their theories and the engine discovers additional sources
- **Open researcher workspace:** the researcher names their theories and corpus

### 2. Whose instruments define testability

- **Consciousness demo:** the field's instruments (fMRI, EEG, TMS, etc.)
- **Physics workspace:** physics instruments (LHC, LIGO, IceCube, Vera Rubin, etc.)
- **Any new domain:** the domain's instruments, authored into the capability map

### 3. What the output looks like

- **Consciousness demo:** four interactive screens (blind recovery, failure autopsy, field matrix, live predictions)
- **Physics workspace:** correspondence cards, experiment paths, rejection ledger
- **Researcher workspace:** configurable views over the same data

### 4. Which domain pack the ontology runs

- **Consciousness:** claim kinds include locus, temporal_profile, connectivity, substrate_dependence, computability, mechanism, observable_commitment
- **Physics:** claim kinds include substrate, mechanism, architecture, measurement, location, scale, boundary
- **Extensible:** any domain where a domain pack has been authored (claim kinds, relation types, scale enum, capability map)

## Nothing else changes

The extraction pipeline is the same. The typed graphs are the same. The matching is the same. The grading ladder is the same. The equivocation test is the same. The decidability check is the same. The provenance manifest is the same.

One engine. Four config points. Every domain is a configuration, not a rebuild.
